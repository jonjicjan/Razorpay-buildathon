The track is intended to identify risk-aware, ML-minded builders.

Therefore the final project must be designed so that:

- The main functionality can be demonstrated quickly.
- The video can show the actual system working, not only slides.

- We can explain technical tradeoffs.

==================================================
5. HOW THEY EVALUATE THE WORK
==================================================

They state:

"We read the work, not the resume."

"We look at how you think, build and solve problems."

Their four evaluation dimensions are:

A. PROBLEM TASTE

Question:
"Did you pick something that actually matters?"

Therefore evaluate every idea on:
- severity of the loss
- frequency of occurrence
- financial impact
- practical merchant pain
- relevance to payments/risk
- whether the problem is sufficiently narrow
- whether solving it creates measurable value
- whether the problem is realistically solvable by a student team

Avoid vague problems.

Prefer:
- one concrete class of loss
- one measurable outcome
- one clear user
- one clear workflow

B. BUILD QUALITY

Question:
"Does it run, is it structured, would you trust it?"

Therefore evaluate:
- reliability
- architecture
- code quality
- testability
- reproducibility
- data pipeline
- model pipeline
- API design
- error handling
- observability
- deployment/run instructions
- security
- documentation

C. AI JUDGMENT

Question:
"The right tool in the right place, and where you chose not to use one."

This is EXTREMELY IMPORTANT.

Do not add AI merely because the hackathon is about AI.

For every AI component, explain:
- Why AI is needed.
- Why a deterministic rule is insufficient.
- Why an ML model is appropriate.
- Why an LLM is or is not appropriate.
- Where deterministic logic is safer.
- Where probabilistic models are useful.
- Where human approval is required.
- Where AI should explicitly NOT be used.

A strong project may deliberately use:
- rules
- statistics
- classical ML
- anomaly detection
- embeddings
- LLMs
- workflow automation

But only where each component is justified.

D. FAILURE RECOVERY

Question:
"What broke, and what did you do about it?"

The final project must include real engineering failures.

Track:
- failed experiments
- bad models
- data problems
- false-positive problems
- latency issues
- API failures
- deployment failures
- prompt/model failures
- architectural mistakes

For each important failure document:
1. What happened?
2. Why did it happen?
3. How did we detect it?
4. What did we change?
5. What improved afterward?

Never invent fake failures.

==================================================
6. HARD REQUIREMENTS OF THE TRACK
==================================================

These are non-negotiable.

The project MUST:

1. Focus on ONE class of loss.

Possible categories include:
- fraud
- returns
- chargebacks
- abuse
- another clearly defined merchant-loss category

Do NOT attempt to solve all risk problems simultaneously.

2. Produce a measurable prediction, verification decision, or response.

3. Use a held-out test set.

4. Report precision.

5. Report recall.

6. Report false-positive cost.

7. Be defense-only.

8. Have a reproducible implementation.

9. Be demonstrable in approximately five minutes.

10. Have an architecture that can be clearly explained.

==================================================
7. DEFENSE-ONLY SAFETY REQUIREMENT
==================================================

The system must only help detect, prevent, verify, investigate, or respond to risk.

It must NOT:
- enable fraud
- generate attack instructions
- help evade fraud detection
- optimize attacks
- produce credential theft workflows
- create malware
- help bypass payment controls
- provide exploitation instructions
- create offense-capable tooling

If an idea has dual-use potential, redesign it toward defensive monitoring, detection, verification, investigation, or controlled response.

If an idea cannot clearly satisfy the defense-only requirement, reject it.

==================================================
8. ML EVALUATION REQUIREMENTS
==================================================

This is not a project where we can say:

"Accuracy = 95%"

and stop.

You must force us to think about:

- class imbalance
- precision
- recall
- confusion matrix
- false-positive rate
- false-negative implications
- threshold selection
- calibration where appropriate
- held-out evaluation
- data leakage
- temporal leakage
- train/test contamination
- baseline comparison

The evaluation must answer:

"Does this system actually detect the target loss better than a reasonable baseline?"

We should compare against:
- simple rules
- naive baseline
- classical ML baseline
- final model

where appropriate.

==================================================
9. FALSE-POSITIVE COST IS A FIRST-CLASS METRIC
==================================================

Do NOT treat false positives as an afterthought.

For example, a false positive can cause:
- legitimate customer blocked
- payment declined
- merchant revenue lost
- unnecessary manual investigation
- customer dissatisfaction
- unnecessary support costs

Therefore we must define a realistic cost function.

Ask:
- What does a false positive cost?
- What does a false negative cost?
- Which error is more expensive?
- What threshold minimizes expected business loss?
- Can risk levels be tiered rather than binary?

Evaluate both:
ML metrics
AND
business metrics.

==================================================
10. DATA REQUIREMENTS
==================================================

Do not invent real-world data and pretend it is real.

First determine:
- What data is actually available?
- Is it public?
- Is it synthetic?
- Can we create realistic synthetic data?
- Is there a legitimate benchmark?
- What labels exist?
- Are labels noisy?
- How will we create train/validation/test splits?
- Can the test set remain untouched?

If synthetic data is used:
- explicitly state that it is synthetic
- explain how it was generated
- avoid unrealistic distributions
- inject realistic edge cases
- preserve class imbalance where appropriate
- create the held-out set independently

Do not fabricate performance from imaginary data.
